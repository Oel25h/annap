# Current state of the site (map taken 2026-10-22, before the redo)

Generated from six parallel code readers plus gap follow-ups, against commit 8429c6d. Line numbers may drift as the redo lands. This is a snapshot for planning, not a spec.


## public-pages

Public pages are hand-written, one-off React components per route (no section model). The /el/* twins are thin files that reuse the English component and hand-copy their own head() blocks. Locale comes from the pathname via LocaleProvider. UI and most long-form copy (bio chapters, values, book chapters, foundation copy, stats text) sit in src/lib/i18n/messages/{en,el}.ts; Supabase only overlays some fields. Only /blog/$slug and /foundation load data in a route loader. Every other page fetches Supabase with the anon client inside useEffect, so the SSR HTML shows empty "coming soon" states, src/data/site.ts placeholder content, or English fallbacks until hydration. Greek overlays come from content_translations (approved only), fetched one row at a time with no stale check. LocaleLink renders a plain <a>, so every internal navigation is a full document reload. LocaleDetect then does a client-side redirect based on a cookie or the browser language. Several bugs are confirmed. /el/foundation throws, because FoundationPage calls Route.useLoaderData() bound to /foundation. The root adds a canonical to the homepage on every page, so each page has two canonicals. Masterclasses renders the literal text "{t.masterclasses.sub}". Foundation story HTML is not sanitized. The sitemap lists /books/{slug} URLs that have no route. The current fonts (Space Grotesk / DM Sans) have no Greek glyphs. The existing build has a 627KB (192KB gzip) entry chunk that includes sanitize-html, postcss and framer-motion. Assets are plain JPGs with no srcset, width/height, WebP/AVIF or priority hints. The plan of reusing components across locales, the translation overlay helpers, the loader pattern, the honeypot/zod server functions and the unsubscribe token flow are worth keeping. The page bodies, header, footer, media and SEO layers need to be rebuilt around a Supabase section registry.

## studio

The studio is 13 client-only screens under src/routes/_authenticated (ssr:false). Access is gated by useAdmin, which reads user_roles in the browser. Almost every write goes straight from the browser Supabase client to the tables and the 'media' bucket, so RLS has_role policies are the only server-side check. Only Books (books.functions.ts) and the Greek translation flow (translate.functions.ts) use server functions that re-check has_role, plus createFirstAdmin for bootstrap. Each screen is a hand-written form tied to one table, with no shared form layer. There is no Zod on client writes, no dirty tracking or unsaved-changes guard, no pagination (every list is an unbounded select('*')), and lists show full-size originals as thumbnails. Most screens ignore the {error} that supabase-js returns. Blog, Products and Newsletter close the editor anyway, and Masterclass, Pages and Start still show a 'Saved' toast, so failed saves silently lose work. Greek uses one GreekTranslationPanel per entity (Gemini draft, then proofread, then approve into content_translations). But Foundation translations always fail Zod, 'stale' is never computed, Regenerate takes approved Greek off the live site, and there is no queue view. Uploads go unprocessed to a public bucket (10MB cap, no resize/WebP/AVIF, progress, retry, alt text or media table), and files are never deleted. Several screens write data the public site does not read: product_images is not shown on /shop, and gallery section order and renames do not reach /gallery. Visually it is a pill and rounded-3xl theme with shadows and hex literals, all English, none of it in i18n messages. Overall it is a usable single-admin CMS for fixed pages. Measured against the redo it is mostly missing: no section registry, nav/footer/site settings, SEO, redirects, versions, previews, Cmd+K, 2FA, audit log, media library, translations queue, Stripe, Resend, videos or audiobooks.

## data-security

Supabase project extyqqkasmchctvoltbm (supabase/config.toml) has 12 migrations defining 22 public tables, one enum (app_role='admin'), has_role(), two updated_at trigger functions and one public 'media' storage bucket. Every table has RLS on. The pattern is the same everywhere: public SELECT (often USING true, sometimes status-filtered) and an admin-only FOR ALL via has_role(auth.uid(),'admin'). contact_messages and subscribers still allow anonymous INSERT directly. Content is modeled per page (start_page_*, masterclass, foundation_settings, page_content key/value) rather than as sections. Greek is an overlay in content_translations (draft/approved only). Most studio CRUD (about 80 calls in src/routes/_authenticated/admin.*.tsx and SocialsManager.tsx) writes straight from the browser with the user JWT and relies on RLS alone: no Zod, no server-side has_role re-check, no audit. Only books (books.functions.ts) and translations (translate.functions.ts) go through server functions with requireSupabaseAuth plus a has_role RPC. The service-role client is used correctly via dynamic import (a grep of the built client assets found neither secret value). It powers the contact and subscribe forms, unsubscribe and first-admin bootstrap. types.ts has drifted: the three foundation tables are missing (32 'as never' casts) and content_translations was hand-inserted out of order. Repo notes show prod was changed out-of-band (bucket created via the Storage API, live rows patched), so the real prod schema is unknown. Missing for the redo: MFA, audit log, versions, a media table, orders/donations/leads/audiobooks/videos, site settings/navigation/pages/sections, redirects, and a Stale translation state. Signup closure cannot be verified from the repo.

## i18n

The locale comes only from the URL. getLocaleFromPath (src/lib/i18n/locale.ts:12) treats /el and /el/* as Greek and everything else as English. LocaleProvider (context.tsx:16-23) works it out from the router pathname, so SSR never reads a cookie or Accept-Language. After hydration, LocaleDetect (LocaleDetect.tsx:22-51) sends the visitor to the aph_locale cookie's locale with replace. If there is no cookie and the browser prefers Greek, it writes cookie=el and redirects. This happens on every full page load, because LocaleLink is a plain <a> (LocaleLink.tsx:42) and the public site uses no TanStack <Link>. LocaleSwitcher writes the cookie and calls router.navigate to the twin path, keeping the query string but dropping the hash. That is an SPA navigation, not a reload, but the twin is a different route match: the component remounts and re-runs every client-side Supabase fetch, and on EL it adds one content_translations query per item. UI messages are typed: `el: Messages`, with en as the source of truth via DeepStringLeaves. Key parity is exact: 319 leaf strings and 260 named keys in each file, nothing missing on either side, and about 11 keys never used. The catalogs also hold real content (about-page biography, book chapters, foundation copy, stats). CMS overlay: one content_translations row per (entity_type, entity_id, locale), holding fields jsonb, status draft|approved and a source_hash. Public reads filter status='approved' and RLS only exposes approved rows to anon, so drafts cannot leak through queries. However, a hard-coded Greek map (start.tsx:14) and launch-time Gemini output that was auto-approved (per .ralph audit notes) put unreviewed Greek on the live site. Gemini drafting is admin-only through server functions that re-check has_role. The API key stays server-side, the model is set by env with a default of gemini-3.6-flash, and output is structured JSON. There is no timeout, retry or rate limit, and stale detection is never computed. All public CMS data except blog posts and foundation is fetched client-side in useEffect, so SSR of /el pages contains English fallbacks. ## design-frontend

The site runs a coral/cream "memoir luxury" system set in src/styles.css (Tailwind 4 @theme). Its brand tokens have misleading names (--plum = #1a1a1a charcoal, --burgundy = #e85d3a coral, --gold = #f4a582 peach), and a name freeze in DESIGN.md / TOKEN_FREEZE.md forbids renaming them. App code uses those brand utilities directly: plum 596 uses, burgundy 362, ivory 212. The shadcn semantic tokens (bg-primary, text-muted-foreground…) appear 0 times outside src/components/ui, and none of the 45 shadcn components (4,033 lines) is imported by app code. Each route instead copies long Tailwind class strings for CTAs and eyebrows, uses inline coral rgba shadows, and stacks radii from rounded-full (204) to rounded-[2.5rem]. Typography is Space Grotesk + DM Sans, loaded from styles.css:4-5. Neither font ships a Greek subset, so every /el page falls back to system fonts. Noto Serif Display, Source Serif 4 and Noto Sans are in package.json with Greek subsets but are never imported. Fraunces and Inter are installed and also never imported. The look is the opposite of the new flat direction: soft-shadow utilities (109 uses), hover lifts, glass backdrop-blur pills in 9 files, gradient stages, a blur orb, and no dark mode. Framer Motion runs in 6 files with sensible reduced-motion handling in Reveal and the home page, but not in start/about. Five pages wrap their H1 in Reveal and /start fades its hero in from opacity 0. Most public routes also fetch CMS data client-side in useEffect, so the server-rendered HTML shows fallback copy before the CMS content arrives. Images are JPG/PNG only (about 120–190KB each, already compressed): no srcset, no fetchpriority, 11 of 24 public imgs have no width/height, and there are 14 duplicate image sets between public/ and src/assets plus about 4MB of unused PNGs. Accessibility gaps include a broken skip link (#main does not exist), unlabeled or unassociated form fields, coral 10–11px text at 3.22:1, a gold focus ring at 1.85:1, SSR html lang always "en", and a mobile menu with no focus trap. LocaleLink renders a plain <a>, so every internal navigation is a full page reload of a 626KB main JS bundle. Overall it works and is fairly polished, but almost nothing in the visual layer carries over: tokens, fonts, radii, elevation and components all need replacing, and the behaviors listed under `keep` are worth porting.

### Auth sessions, aal2 (2FA) enforcement, and draft/shareable preview design for the redo

None of the three is decided or written down anywhere in the repo, so each "will" is still an open decision. Nothing depends on @supabase/ssr. No code, migration or spec mentions aal, MFA or TOTP; the only 2FA mention is a wish-list line in .ralph/specs/prod-audit/SUGGESTIONS.md:11. There is no preview route. What follows is the current state, then a recommended design for each.

1) COOKIE SSR SESSIONS: recommend NO for v1.
Today the session lives in localStorage (client.ts:54). attachSupabaseAuth adds a Bearer header to every server-fn RPC (auth-attacher.ts:9-12, registered at start.ts:22). On the server the browser client has no storage, so every SSR read runs as anon (client.ts:35-37,54). The studio is client-only (route.tsx:6).
None of the redo requirements needs the server to know the user:
- Public pages read as anon.
- The studio can stay ssr:false.
- Shareable previews are for anonymous viewers, so they work through tokens (see 3).
Keeping Bearer-only server fns also means no CSRF exposure. If cookies are adopted later for studio SSR, note three costs:
- @supabase/ssr cookies are readable by JS (not HttpOnly), so there is no XSS gain.
- Cookie-authenticated POST server fns would need an Origin/CSRF check. Whether TanStack Start has built-in CSRF protection is unverified.
- Token refresh during SSR on Workers would need setCookie from @tanstack/react-start/server.

2) aal2 ON EVERY WRITE: recommend YES, enforced in three layers. Today nothing checks aal:
- requireSupabaseAuth checks only that the claims exist and claims.sub is set (auth-middleware.ts:88-95).
- has_role reads only user_roles (migration 20260712164300:17-20).
- About 74 write calls in 12 studio files go straight from the browser to tables and storage (biggest: admin.products.tsx 15, admin.foundation.tsx 12, admin.gallery.tsx 12). So turning on TOTP alone would not stop a password-only aal1 session from writing.

(a) SQL: add public.is_admin() = has_role(auth.uid(),'admin') AND (auth.jwt()->>'aal')='aal2'. Use it in every admin policy: 38 has_role references across 6 migrations, including the storage.objects policies (20260712164300:192-194). Admin reads of drafts, messages and subscribers should require it too. Keep "own roles readable" (:15) at aal1 so the studio gate can recognise an admin before MFA.

(b) Server: requireSupabaseAuth should reject when claims.aal != 'aal2'. Add one requireAdmin middleware to replace the duplicated assertAdmin helpers (books.functions.ts:28-34, translate.functions.ts:31-42). This layer is mandatory, not optional: the translation fns write with the service role (translate.functions.ts:262-285, 293-312, 320-333), which bypasses RLS. The same will apply to future Stripe, Resend and media fns.

(c) Client: the useAdmin hook and the studio gate (useAdmin.ts:23-34, route.tsx:12-16) should call supabase.auth.mfa.getAuthenticatorAssuranceLevel(). An aal1 admin is sent to an enrol or challenge screen; the MFA API calls themselves work at aal1.

Bootstrap and recovery:
- createFirstAdmin creates a password-only user (admin.functions.ts:34-38), so the first sign-in must force TOTP enrolment.
- The ADMIN_SETUP_SECRET path refuses once any admin exists (admin.functions.ts:30-32), so a lost authenticator has no in-app recovery. Plan for it: enrol 2 TOTP factors, or keep a service-role reset script.
- The roughly 74 direct browser writes keep working under aal2 RLS. They should still move behind server fns so the audit log and version history can record them.

3) PREVIEWS: recommend a stored opaque token, not a stateless signed one. Nothing exists today:
- Public loaders hard-filter status='published' (blog.$slug.tsx:37; 9 call sites).
- Anon RLS on the content tables (posts, books, products) is published-only (e.g. 20260712164300:45,90,131).

Two separate paths:
(a) Draft rendering inside the studio needs no token. The aal2 admin session reads drafts through the "admins read all" policies (:46,91,132). Page loaders take mode='published'|'draft', and draft mode is reachable only through requireAdmin or a valid token.

(b) Shareable links:

- Scope: one entity (page, post or book) with its sections, referenced media and translations, both locales, read-only, showing the live latest draft, with an optional pinned version_id.
- Expiry: 7 days by default, 30 days at most. The token can be revoked at any time.
